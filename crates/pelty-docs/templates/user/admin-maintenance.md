# Backups and upgrades

## Backups

Admin → System & settings → **Backups** creates a **full site archive** (zip) as a background job (`backup.site`), lists them, downloads them and deletes them. Files are written to `PELTY_BACKUP_DIR` (default `./backups`); file names are generated by the server (`pelty-….zip`).

{{env:PELTY_BACKUP_DIR,PELTY_PG_DUMP}}

Each archive contains:

| Path in the zip | Contents |
|-----------------|----------|
| `database.dump` | PostgreSQL custom-format dump (`pg_dump -Fc`) |
| `files/addons/` | Installed addon packages (`PELTY_ADDONS_DIR`) |
| `files/addon-data/` | Per-addon data when separate from packages (`PELTY_ADDON_DATA_DIR`) |
| `files/themes/` | Themes (`PELTY_THEMES_DIR`) |
| `files/plugins/` | Webhook plugins (`PELTY_PLUGINS_DIR`) |
| `files/media/` | Uploaded brand/site images (`PELTY_MEDIA_DIR`) |
| `files/locales/` | UI translation JSON (`PELTY_LOCALES_DIR`) |
| `config/.env` | Install config including `PELTY_ENCRYPTION_KEY` |
| `config/eula.txt` | EULA acceptance file |
| `manifest.json` | What was included and restore hints |

Ticket attachments and most product data live in the database, so they are in `database.dump`. The zip **does not** include the local Postgres data directory (`data/pg`), other backup files, or the server binary.

Keep copies off the server: the archive holds secrets (encryption key, DB password in `.env`).

### Restore

1. Unpack the zip next to a fresh install (or over an existing one for the `files/` and `config/` trees).
2. Restore Postgres into an empty database:

```bash
pg_restore --clean --if-exists --no-owner -d "$DATABASE_URL" database.dump
```

3. Copy `config/.env` (keep the same `PELTY_ENCRYPTION_KEY`) and `config/eula.txt`, then start `pelty-server`.

## Upgrades

Once released, PeltyCMS is planned to ship as a binary or container image, so upgrading will be a redeploy:

- Take a backup.
- Replace the binary or pull the new image.
- Restart. `pelty-server serve` applies new database migrations on start (`pelty-server migrate` runs them on their own).

The daily `system.update_check` job compares the running version with the latest release and shows staff a banner with the release notes link. The release feed URL and on/off switch are stored under `update_check`. The [Database migrations](developers/migrations.md) page lists every migration.

## Health

Admin → System & settings → **System health** runs the system health checks. `/healthz` answers `ok` for load balancers and container health checks.
